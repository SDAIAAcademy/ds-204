The case study

Sullam Vocational Training Fund wants to offer support early

The fund

A fictional fund that pays for programmes at 60 providers in 13 regions. 45,000 synthetic enrolments, 30,000 trainees, cohorts 2021 to 2025.

The problem

Break-even

A plan pays when p × 0.25 × 9,000 > 450: when the probability of not completing is above 0.20.

The figures belong to Ghassan Al-Fayez, in data/decision.json, not to the data scientist. Notice already: the base rate, 0.119, is below the break-even, 0.20, so supporting everyone loses money. And the costs leave out the cost to the trainee, which no table prices. Day 4 turns capacity and break-even into a threshold.

Responsible use

  • The purpose is narrow: decide whom to offer support

Rung 1

The floor of average precision is the base rate, not 0.5

0.118
average precision of the same score for everyone, mean of five folds
  • Average precision: precision averaged over every position where a non-completer is found
  • A ranking with no information has the base rate as its precision everywhere
  • ROC AUC is the score whose floor is 0.5
  • For a rare outcome and a short list, average precision is the stricter judge

From Lab 1.2: the constant scores exactly the base rate on each fold, 0.108 to 0.130. Why average precision and not AUC: AUC counts every pair of a non-completer and a completer equally, including pairs far down the ranking that the advisers never reach; average precision weighs the top of the list, where the 800 names are. Sources: Saito and Rehmsmeier (2015).

Rung 3

A linear model is the first model worth beating

  • Logistic regression: a weighted sum of the inputs, turned into a probability
  • Its probabilities are usually close to observed rates
  • Each weight can be read, with care
  • On tables with mostly additive effects it is hard to beat by much

What it cannot do alone

It adds effects. "Absence matters, except for employer-sponsored trainees" is an interaction: someone has to write it in, or a tree has to find it. That is Day 2.

FN-103 gave the mathematics: the log-odds are linear in the inputs. The practical point for a ladder: if a tuned boosted model beats this rung by less than the folds disagree, the organisation may prefer the model it can read. Keep that open; Day 2 measures it.

From Lab 1.3. The "was missing" column lets the model learn that a missing entry test means something, which here it does. In code

The whole rung is one object that can be fitted and scored

numeric = Pipeline([("impute", SimpleImputer(strategy="median", add_indicator=True)),
                    ("scale", StandardScaler())])
categories = Pipeline([("fill", SimpleImputer(strategy="constant", fill_value="not recorded")),
                       ("onehot", OneHotEncoder(handle_unknown="infrequent_if_exist",
                                                min_frequency=30, sparse_output=False))])
prepare = ColumnTransformer([("num", numeric, NUM), ("cat", categories, CAT)])
model = Pipeline([("prepare", prepare),
                  ("model", LogisticRegression(C=0.1, max_iter=2000))])
One object, one rule. Whatever is inside the pipeline is refitted in every fold. Whatever you compute before it has seen every row.

This is the exercise of task 1; participants who did the pre-work write it in a few minutes. Keep this slide short: the code is in the lab.

What the pipeline protects

The harm of preparing outside the folds depends on what the step has read

PreparationMean scoreVerdict
Imputer and scaler inside each fold0.5013the reference
Imputer and scaler fitted on all rows0.5014wrong, and almost free
Provider rate from training rows0.5018honest
Provider rate from all rows0.5041the gain is false
What goes wrong. A step that never sees the outcome leaks little. A step built from the outcome (a rate per provider, a feature selection, a tuned setting) leaks in proportion to what it read.

From Lab 1.3, step 4. Be honest about the sizes: on 30,000 rows a median read from all rows moves the fourth decimal. The principle is not "the score explodes" but "you cannot know how much without redoing it properly", and the pipeline makes the question disappear. The larger versions of the same fault are on Day 3. Sources: scikit-learn user guide, Common pitfalls and recommended practices.

A test, not a promise

The time-travel test hides the future and checks that nothing changes

1 · Pick a past dateFor example 1 March 2023
→
2 · Compute twiceFrom all records, and from the records ended by that date
→
3 · CompareFor every row predicted before that date
  • A feature that reads the past only gives the same value both times
  • The "started earlier" version changes for about 90 rows at each date: it fails
  • The test checks the features, not the model, and takes seconds

From Lab 1.4, where U.time_travel_test runs three dates. This is the tabular cousin of a unit test, and the capstone rubric rewards one. It proves that hiding later records does not change a feature. It does not prove the feature is useful, and it says nothing about the columns you did not build.
